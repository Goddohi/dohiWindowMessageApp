# 자동 시작 최소화 상태의 수신 리스너 보장

- 상태: 완료
- 우선순위: 1차 안정화
- 관련 영역: 앱 시작, 트레이, TCP 수신

## 왜 고려했는가

자동 시작을 켠 사용자는 프로그램이 트레이에 떠 있으면 메시지를 받을 수 있다고 기대합니다.

하지만 최소화 시작 상태에서 수신 리스너가 시작되지 않으면 사용자는 프로그램이 켜져 있는데도 메시지를 받지 못합니다. 이 문제는 상대방 입장에서는 전송 실패처럼 보이고, 수신자 입장에서는 나중에야 누락을 알게 되는 형태라 체감 영향이 큽니다.

## 현재 원인

자동 시작은 `--minimized` 인자를 붙여 실행합니다.

앱 시작 로직은 이 인자를 감지하면 메인 창을 만들지 않고 바로 반환합니다. 그런데 현재 TCP 수신 리스너는 `MainWindow` 생성자 안에서 시작됩니다.

결과적으로 최소화 자동 시작 상태에서는 트레이 아이콘은 보이지만, 메시지 수신 리스너가 준비되지 않을 수 있습니다.

## 해결 방향

### 단기 안정화

최소화 시작이어도 `MainWindow`를 숨긴 상태로 생성합니다.

이 방식은 현재 구조를 크게 바꾸지 않고 다음 효과를 얻습니다.

- 기존 `MainWindow` 초기화 흐름을 그대로 사용합니다.
- `ChatListManager`, 사용자 정보, 친구 목록, TCP 수신 리스너가 정상 초기화됩니다.
- 창은 사용자에게 보이지 않고 트레이 상태로 대기합니다.
- 이후 트레이에서 열기를 누르면 이미 생성된 창을 보여줍니다.

## 해결 내용

`App.OnStartup`에서 `--minimized` 인자를 감지하면 바로 반환하지 않고 숨김 메인 창을 초기화하도록 변경했습니다.

적용 방식:

- `InitializeHiddenMainWindow`를 추가했습니다.
- 숨김 시작 시 `MainWindow`를 생성해 기존 초기화 흐름을 실행합니다.
- `WindowInteropHelper.EnsureHandle`로 윈도우 핸들을 미리 만들어 단일 인스턴스 복원 메시지도 받을 수 있게 했습니다.
- 창은 `Hide` 상태로 유지해 사용자에게 표시하지 않습니다.
- 일반 실행과 트레이 열기는 `EnsureMainWindowCreated`를 통해 기존 창을 재사용합니다.

이 해결은 현재 구조를 크게 흔들지 않는 단기 안정화입니다. 이후 수신 리스너는 `MessageReceiverService`로 분리했습니다.

### 장기 개선

수신 리스너는 UI 창에 묶이지 않는 앱 서비스로 분리하는 것이 더 적절합니다.

장기 구조는 다음 방향이 좋습니다.

- 앱 시작 시 백그라운드 수신 서비스 시작
- UI는 수신 이벤트를 구독
- UI가 없어도 텍스트/파일 메시지를 저장
- MainWindow는 표시와 상호작용만 담당

## 완료 조건

- `--minimized` 시작 시 창이 뜨지 않습니다.
- `--minimized` 시작 시에도 TCP 수신 리스너가 시작됩니다.
- 트레이에서 열기를 누르면 기존 창이 표시됩니다.
- 일반 실행 시 기존처럼 메인 창이 표시됩니다.
