# UUID/친구추가 QA 오류 정리

- 상태: 검증 중
- 우선순위: 1차 안정화
- 관련 영역: 127.0.0.1 테스트, UUID 수신 저장, 친구 추가 UX, 전송 실패 테스트
- 정리일: 2026-08-31
- 최근 갱신일: 2026-09-02

## 현재 실행 상태

- 앱은 실행 중입니다.
- `WalkieDohi.exe` 프로세스가 응답 중입니다.
- TCP 수신 포트 `9000`은 `0.0.0.0:9000`으로 리슨 중입니다.
- 최신 빌드는 성공했습니다.
- 빌드 오류는 없습니다.
- 빌드 경고는 기존 미사용 변수/이벤트 경고가 남아 있습니다.
- 2026-09-02 기준 UUID/그룹/친구 추가 흐름은 "IP 고정 + UUID 힌트 보강" 단계입니다.

## 오류 1: 127.0.0.1 테스트 메시지가 화면에 안 보임

### 현상

예전에는 `127.0.0.1`로 자기 자신에게 테스트 메시지를 보내면 채팅 화면에 표시되었습니다.

UUID/메시지 중복 방지 작업 이후 `127.0.0.1` 테스트 메시지가 답장처럼 다시 보이지 않는 문제가 발생했습니다.

### 원인

직접 원인은 UUID 자체가 아니라 `MessageId` 기반 중복 방지 로직입니다.

`127.0.0.1` 테스트는 같은 앱이 보낸 메시지를 같은 앱이 다시 받는 로컬 echo입니다. 이때 송신 화면 메시지와 수신 메시지가 같은 `MessageId`를 가지므로, 수신 처리에서 이미 저장된 메시지로 판단하고 화면 표시까지 막았습니다.

### 조치

- 로컬 echo 여부를 `SenderUserUuid == 내 UserUuid`와 `SenderIp == loopback` 기준으로 판정합니다.
- 이미 열린 채팅방이 있으면 로컬 echo는 화면에는 표시합니다.
- 대신 DB에는 중복 저장하지 않습니다.

### QA 기준

- `127.0.0.1`로 텍스트를 보내면 화면에 표시되어야 합니다.
- 같은 메시지가 DB에 2건 저장되면 안 됩니다.
- 파일/이미지 로컬 echo도 같은 기준으로 확인이 필요합니다.

## 오류 2: 127.0.0.1로는 친구 UUID 저장 검증이 안 됨

### 현상

`127.0.0.1`로 테스트하면 UUID 기반으로 친구가 저장되는지 헷갈릴 수 있습니다.

### 원인

`127.0.0.1`은 자기 자신에게 보내는 테스트입니다. 이 경우 수신된 `SenderUserUuid`는 내 UUID입니다.

내 UUID를 친구 UUID로 저장하면 자기 자신을 친구로 등록하는 문제가 생기므로, 현재 로직은 내 UUID와 같은 수신 UUID는 친구 저장 대상에서 제외합니다.

### QA 기준

- 로컬 echo 테스트는 "메시지 수신 표시" 테스트로만 봅니다.
- 친구 UUID 저장 테스트는 다른 PC 또는 별도 사용자 데이터로 실행한 두 번째 앱에서 확인해야 합니다.

## 오류 3: UUID 기반 전환은 아직 부분 적용 상태

### 현상

현재 코드가 완전히 UUID 기반으로 전환된 것으로 오해할 수 있습니다.

### 현재 범위

반영된 부분은 다음입니다.

- 패킷의 `UserUUID`를 수신 메시지에 연결
- 친구 모델에 `UserUuid` 저장 필드 추가
- 기존 IP 친구가 상대 메시지를 받으면 UUID를 연결할 수 있게 처리
- 같은 UUID가 다른 수신 IP에서 들어와도 친구의 저장 IP는 자동 변경하지 않음
- 1:1 미등록 상대와 그룹 멤버에서 `+` 친구 추가 버튼 제공
- 친구 추가 창에 IP를 미리 입력
- 그룹 패킷에 멤버별 `Ip` + `UserUuid` 힌트를 함께 보낼 수 있게 처리

아직 남은 부분은 다음입니다.

- 개인 채팅방 key를 `user_{uuid}`로 완전 전환
- 기존 IP room key를 UUID room key로 병합
- UUID 기반 방 병합 검증

### QA 기준

- 지금 단계에서는 IP 기반 전송과 기존 채팅방 구조가 유지됩니다.
- UUID는 우선 "상대 식별 정보 저장"과 "수신 메시지 재매칭"에 사용됩니다.
- 완전한 UUID 방 병합은 별도 단계로 검증해야 합니다.

## 오류 4: 실패 테스트 IP로 999.999.999.999를 쓰면 안 됨

### 현상

전송 실패 테스트용으로 `999.999.999.999`를 넣을지 논의가 있었습니다.

### 원인

`999.999.999.999`는 유효한 IPv4 주소가 아닙니다. 이 값은 네트워크 전송 실패가 아니라 입력값 검증 실패에 가깝습니다.

### 조치 방향

전송 실패 테스트는 유효하지만 도달하지 않는 테스트용 IP를 사용합니다.

권장값은 `192.0.2.1`입니다.

### QA 기준

- 입력값 검증 테스트: `999.999.999.999`
- 전송 실패 테스트: `192.0.2.1`
- 정상 로컬 수신 테스트: `127.0.0.1`

## 오류 5: 그룹/모르는 사람 친구 추가 시 IP 확보 범위

### 현상

그룹원이거나 모르는 사람일 때 `+`로 친구 추가를 바로 하고 싶습니다.

### 현재 처리

- 1:1 미등록 채팅방 헤더에 `+` 버튼을 표시합니다.
- 그룹 멤버 목록에서 친구가 아닌 IP 옆에 `+` 버튼을 표시합니다.
- 버튼을 누르면 친구 관리 창이 열리고 IP가 미리 입력됩니다.
- 사용자는 이름을 입력한 뒤 바로 친구로 추가할 수 있습니다.

### 한계

IP는 앱이 임의로 알아낼 수 없습니다. 현재는 다음 값이 있을 때만 미리 입력할 수 있습니다.

- 수신 패킷의 `packet.MyIp`
- 메시지의 `SenderIp`
- 그룹의 기존 `Ips` 목록
- TCP remote endpoint fallback

즉, "아직 아무 통신도 하지 않은 모르는 사람"은 IP를 직접 입력해야 합니다.

### QA 기준

- 미등록 1:1 방에서 `+` 버튼이 보이는가.
- `+`를 누르면 IP가 미리 채워지는가.
- 이름 입력 후 친구 추가가 되는가.
- 그룹 멤버 목록에서 친구가 아닌 멤버만 `+`가 보이는가.

## 오류 6: 친구 추가의 연결 확인과 UUID 저장 범위

### 현상

IP만 입력해서 친구를 추가하면 상대 UUID를 모른 채 저장됩니다.

### 원인

UUID는 상대 앱이 보내주는 패킷을 받아야 알 수 있습니다. 상대 앱이 켜져 있지 않거나 없는 IP이면 연결 확인과 UUID 조회를 할 수 없습니다.

단, IP는 사용자가 지정한 전송 대상 주소이므로 연결 확인 성공 여부와 별개로 저장값을 자동 변경하지 않습니다.

### 조치

- 친구 추가 창에 `연결확인` 버튼을 추가합니다.
- `+` 버튼으로 IP가 미리 입력된 경우에는 창이 열린 뒤 자동 연결 확인을 한 번 시도합니다.
- 상대 앱이 켜져 있으면 `ProfileRequest`를 보내고 `ProfileResponse`에서 UUID/닉네임을 받습니다.
- 연결 확인 성공 시 상대가 지정한 닉네임을 이름 입력칸에 자동 입력합니다.
- 사용자는 자동 입력된 이름을 수정할 수 있고, 저장 시 사용자가 최종 입력한 이름과 `UserUuid`를 저장합니다.
- 연결 확인 실패 시 다음 문구를 표시합니다.

`상대방의 프로그램이 꺼져있거나 없는 IP 입니다`

### QA 기준

- 상대 앱이 켜져 있으면 연결 확인 성공 후 이름과 UUID가 저장되는가.
- 상대 앱이 꺼져 있으면 지정 문구가 표시되는가.
- 없는 IP이거나 응답이 없으면 지정 문구가 표시되는가.
- 연결 확인 실패 후에도 수동 이름/IP 입력으로 친구 추가가 가능한가.
- 연결 확인 성공 후에도 저장 IP가 응답 IP로 자동 변경되지 않는가.
- 연결 확인 성공 후 IP를 바꾸면 이전 UUID가 저장되지 않는가.
- 내 UUID가 응답되면 자기 자신 친구 추가를 조회 단계와 저장 단계에서 모두 막는가.
- `127.0.0.1` 또는 내 로컬 IP를 직접 입력해도 자기 자신 친구 추가가 막히는가.
- 친구 추가가 완료되면 `{이름}님이 추가되었습니다.` 안내가 표시되는가.

## 오류 7: 친구 추가 후 채팅방 목록/헤더가 바로 바뀌지 않음

### 현상

미등록 상대를 `+` 버튼으로 친구 추가한 뒤에도 채팅방 목록 또는 오른쪽 채팅 헤더의 표시가 바로 바뀌지 않을 수 있습니다.

### 원인

친구 관리 창이 정렬된 복사본 컬렉션을 편집한 뒤 파일에 저장합니다. 저장된 친구 목록은 `MainData.Friends`로 반영되지만, 이미 열린 채팅방 목록과 헤더는 별도 갱신 신호가 없어서 기존 표시를 유지할 수 있었습니다.

또한 `+` 버튼으로 연 친구 추가 창은 추가 후에도 창이 계속 열려 있어, 부모 채팅 화면의 갱신이 사용자가 창을 닫은 뒤에야 실행될 수 있었습니다.

### 조치

- 친구 목록 저장 시 채팅방 목록의 1:1 이름을 현재 친구 이름으로 다시 동기화합니다.
- `MainData.FriendsChanged` 이벤트를 추가해 친구 변경을 열린 채팅방 화면에 전달합니다.
- 열린 1:1 채팅방 헤더를 친구 변경 후 다시 그립니다.
- `+` 버튼으로 연 친구 추가 창은 추가 성공 시 바로 닫히게 했습니다.
- 채팅방 목록 항목과 친구 항목이 속성 변경을 UI에 알리도록 `INotifyPropertyChanged` 연결을 보강했습니다.

### QA 기준

- 미등록 1:1 방에서 `+`로 친구를 추가하면 창이 닫힌 뒤 헤더 이름이 즉시 바뀌는가.
- 채팅방 목록의 이름이 친구 이름으로 즉시 바뀌는가.
- 기존 채팅방을 다시 선택해도 이전 이름으로 돌아가지 않는가.
- IP는 아직 전송 대상 주소이므로 보조 정보 또는 괄호 표시는 남아 있을 수 있습니다.

## 오류 8: 사용자별 UUID 확인 방법이 없음

### 현상

테스트 중 각 사용자의 UUID를 직접 확인할 방법이 필요합니다.

### 원인

UUID는 일반 사용자에게 계속 노출할 정보는 아니지만, QA 중에는 내 UUID와 친구로 저장된 상대 UUID를 확인해야 합니다.

### 조치

설정 창에 숨김 테스트 식별자 패널을 추가합니다.

열기 방법은 `Ctrl`을 누른 상태로 설정 제목을 5번 클릭하는 방식입니다.

패널에서 확인 가능한 정보는 다음입니다.

- 내 닉네임
- 내 `UserUuid`
- 친구 이름
- 친구 IP
- 친구 `UserUuid`

친구 UUID는 아직 상대에게서 UUID가 포함된 메시지를 받은 적이 없으면 `(아직 모름)`으로 표시합니다.

### QA 기준

- 설정 제목을 일반 클릭 5번 하면 기존 숨김 동작이 유지되는가.
- `Ctrl`을 누른 상태로 설정 제목을 5번 클릭하면 테스트 식별자 패널이 열리는가.
- 내 UUID가 표시되는가.
- 상대에게 메시지를 받은 뒤 친구 UUID가 표시되는가.
- 복사 버튼으로 내용을 클립보드에 복사할 수 있는가.

## 오류 9: 빌드 경고

## 오류 10: 그룹 UUID 힌트가 친구 UUID로 갱신되지 않음

### 현상

그룹 채팅방의 `Members`에는 각 멤버의 UUID가 있는데, 사용자가 그룹 채팅을 하거나 앱을 다시 열어도 친구 목록의 `UserUuid`가 갱신되지 않을 수 있었습니다.

### 원인

초기 구현은 UUID 보강을 수신 메시지 처리 흐름에 주로 의존했습니다.

따라서 저장된 그룹 정보에 이미 UUID 힌트가 있어도, 그룹방을 갱신하거나 앱을 시작하는 시점에는 친구 목록으로 반영되지 않았습니다.

또한 그룹 메시지 발신자가 기존 `Ips` 목록에 없으면 `Members`에 잠깐 들어갔다가 `RefreshMemberIdentitiesFromFriends()` 과정에서 빠질 수 있어, 초대한 사람 또는 답장한 사람의 UUID 전파가 불안정할 수 있었습니다.

### 조치

- `MainData.TryAttachFriendUuidByIp()`를 추가해 UUID 보강 규칙을 공통화했습니다.
- 그룹 채팅방 갱신 시 그룹 `Members`의 UUID 힌트를 기존 친구 목록에 반영합니다.
- 앱 시작 시 저장된 그룹 목록을 한 번 훑어 기존 친구의 빈 UUID를 보강합니다.
- 앱 시작 시 여러 그룹에서 UUID가 발견되어도 친구 파일 저장은 전체 확인 후 한 번만 수행합니다.
- 그룹 메시지 수신 시 발신자의 `Ip` + `UserUuid`가 그룹 `Members`에 없으면 보존합니다.
- 메시지 본문 `SenderUserUuid`에도 내 UUID를 넣어 패킷 메타데이터가 없어도 식별자를 유지합니다.

### 현재 규칙

- 친구의 IP는 사용자가 지정한 전송 대상 주소이므로 자동 변경하지 않습니다.
- 친구의 `UserUuid`가 비어 있고, 같은 IP 또는 같은 UUID의 기존 친구를 찾을 수 있을 때만 UUID를 채웁니다.
- 친구의 `UserUuid`가 이미 있으면 바로 건너뜁니다.
- 내 UUID와 같은 UUID는 친구 UUID로 저장하지 않습니다.
- 그룹에만 있는 모르는 사람은 친구 목록에 자동 생성하지 않습니다.
- 그룹 `Members`에는 친구 여부와 무관하게 `Ip` + `UserUuid` 힌트를 보존할 수 있습니다.
- 못 받은 사용자는 즉시 갱신되지 않습니다. 이후 내가 다시 답하거나, 이미 UUID를 받은 다른 사용자가 그룹 메시지를 보내면 그룹 힌트가 다시 전파될 수 있습니다.

### 성능 판단

현재 보강 로직은 네트워크 조회가 아니라 저장된 JSON/메모리 객체를 훑는 작업입니다.

채팅방이 많아져도 UUID가 이미 있는 친구는 즉시 건너뛰고, 앱 시작 시 친구 파일 저장은 변경이 있을 때 한 번만 발생합니다.

따라서 현재 테스트 규모에서는 PC 부담이 작습니다. 다만 그룹 수가 수천 개 이상으로 늘어나는 상황을 목표로 한다면, 향후에는 "마지막 보강 시각" 또는 "그룹 변경 버전"을 저장해 변경된 그룹만 검사하는 방식으로 최적화할 수 있습니다.

### QA 기준

- 그룹 `Members`에는 UUID가 있고 친구 `UserUuid`가 비어 있는 상태에서 앱 시작 후 친구 UUID가 보강되는가.
- 그룹 채팅을 보낼 때 그룹 `Members`가 최신 친구 UUID와 내 UUID를 포함하는가.
- 그룹 메시지를 받으면 발신자의 UUID가 그룹 `Members`에 보존되는가.
- 이미 UUID가 있는 친구는 값이 바뀌지 않는가.
- 친구의 저장 IP가 수신 패킷 또는 그룹 힌트로 자동 변경되지 않는가.
- 그룹에만 있는 모르는 사람이 친구 목록에 자동 생성되지 않는가.
- UUID를 받지 못한 그룹원이 이후 다른 사람의 그룹 메시지로 UUID 힌트를 받을 수 있는가.

## PM/QA 판정

현재 가장 중요한 확인은 `127.0.0.1` 로컬 echo 복구와 그룹 UUID 힌트 보강 흐름입니다.

그 다음은 실패 테스트 IP를 분리하는 것입니다. `999.999.999.999`는 입력 검증 케이스로 두고, 실제 전송 실패는 `192.0.2.1`로 확인해야 합니다.

UUID 기반 전체 전환은 아직 완료가 아니라 "IP 고정 + UUID 재매칭 준비 단계"입니다. 다음 개발 단계에서는 개인 채팅방 key를 UUID 기준으로 바꾸고 기존 IP 방을 병합하는 작업이 필요합니다.

친구 목록 자동 생성은 현재 범위에서 제외합니다. 그룹에서 UUID 힌트를 받아도 친구 목록은 이미 등록된 친구만 보강하고, 모르는 사람은 그룹 멤버 정보에만 남깁니다.
