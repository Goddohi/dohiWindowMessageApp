# IP 중심 식별을 사용자 UUID 중심으로 전환

- 상태: 설계 확정
- 우선순위: 3차 식별 체계 개선
- 관련 영역: 친구, 그룹, 채팅방 키, 네트워크
- 설계 확정일: 2026-08-28

## 왜 고려했는가

IP는 사람의 고유 식별자가 아니라 통신 경로의 주소입니다. 특히 다중 랜카드/대표 IP 환경에서는 상대가 나에게 보낼 때 보이는 IP와, 내가 상대에게 보내야 실제 도착하는 IP가 서로 다를 수 있습니다.

따라서 친구에 저장된 IP를 "마지막으로 보인 IP"로 자동 변경하면 오히려 전송 대상이 깨질 수 있습니다. IP는 사용자가 입력한 전송 대상 주소로 고정하고, UUID는 "어느 IP에서 왔든 같은 사람인지"를 묶는 기준으로 사용합니다.

## 현재 원인

- 개인 채팅방 키가 IP입니다.
- 친구 매칭도 IP 중심입니다.
- 그룹 구성원이 IP 리스트입니다.
- 메시지 방향 판정이 내 현재 IP와 `SenderIp` 비교에 의존합니다.
- `UserUuid`는 존재하지만 수신 처리와 채팅방 키에는 충분히 활용되지 않습니다.

## 해결 방향

- 친구 정보에 `UserUuid`, `TargetIp`, `DisplayName`을 분리합니다.
- 채팅방 키는 `UserUuid` 기준으로 변경합니다.
- 그룹 구성원도 `UserUuid` 기준으로 관리합니다.
- IP는 사용자가 입력한 전송 대상 주소로만 사용하며 수신 패킷의 IP로 자동 변경하지 않습니다.
- 친구 추가/수정의 조회 기능은 상대 앱이 해당 IP에서 응답하는지 확인하는 연결 테스트로 사용합니다.
- 기존 IP 기반 데이터는 마이그레이션합니다.

## 확정 원칙

- `UserUuid`는 사용자/설치 단위의 안정 식별자입니다.
- `UserUuid`는 IP, MAC 주소, 닉네임으로 만들지 않고 최초 실행 또는 기존 사용자 파일 보정 시 `Guid.NewGuid()`로 한 번만 생성합니다.
- 저장 위치는 기존 사용자 파일인 `%APPDATA%\WalkieDohi\user.dohi`를 기준으로 합니다.
- 닉네임 변경, IP 변경, 포트 변경, 네트워크 어댑터 변경으로 `UserUuid`를 다시 만들지 않습니다.
- `UserUuid`는 인증 수단이 아닙니다. 같은 폐쇄망 안에서 상대를 안정적으로 묶기 위한 식별자이며, 신뢰/보안 검증은 별도 기능으로 봅니다.
- 기존 `user.json`, `friends.json`, `ChatList.json`, IP 기반 DB room key는 자동 이행 대상으로 보고 삭제하지 않습니다.

## UUID 생성 규칙

- 신규 사용자 파일이 없으면 `User.GetDefaultUser()`에서 UUID를 생성합니다.
- 기존 사용자 파일에 `UserUuid`가 없거나 빈 값이면 `User.UserChecked()`에서 UUID를 생성한 뒤 `user.dohi`로 저장합니다.
- 문자열 형식은 .NET 기본 UUID 형식인 `Guid.ToString("D")`를 표준으로 사용합니다.
  - 예: `866a497c-245c-48cb-87b1-210882633a0f`
- 외부에서 들어온 UUID는 `Guid.TryParse()`로 검증하고, 저장 전 `Guid.Parse(value).ToString("D")`로 정규화합니다.
- 앱 데이터를 복사하면 같은 사용자의 UUID도 같이 복사됩니다. 새 기기로 완전히 다른 사용자처럼 쓰려면 향후 "내 식별자 재생성" 기능을 별도 제공해야 합니다.

## 데이터 모델 결정

### User

`User.UserUuid`는 현재처럼 로컬 사용자의 고유 식별자로 유지합니다.

- `Nickname`: 내가 상대에게 보여줄 현재 이름
- `UserUuid`: 내 고정 식별자
- `Preferences`: 포트, 정렬 등 환경 설정

### Friend

친구는 사람 식별자와 전송 대상 주소를 분리합니다.

- `UserUuid`: 친구의 고정 식별자
- `DisplayName`: 내가 보는 친구 이름
- `TargetIp`: 내가 이 친구에게 보낼 때 사용할 고정 IP
- `LastSeenNickname`: 상대가 패킷에 실어 보낸 마지막 닉네임
- `DisplayName`은 사용자가 직접 정한 이름을 우선하며, 수신 패킷의 닉네임으로 임의 덮어쓰지 않습니다.
- `TargetIp`는 사용자가 직접 입력/수정한 값만 반영하며, 수신 패킷의 `SenderIp` 또는 `packet.MyIp`로 자동 덮어쓰지 않습니다.

기존 필드와의 호환 규칙은 다음과 같습니다.

- 기존 `Name`은 `DisplayName`으로 이행합니다.
- 기존 `Ip`는 `TargetIp`로 취급합니다.
- 코드 전환 중에는 `Name`, `Ip`를 바로 삭제하지 않고 legacy alias 또는 migration input으로 둡니다.

### ChatListItem

친구로 등록하지 않은 상대와의 대화도 유지해야 하므로 채팅 목록에도 최소 식별 정보를 둡니다.

- `RoomKey`: 실제 채팅방 key
- `PeerUserUuid`: 개인 채팅 상대 UUID
- `PeerDisplayName`: 채팅 목록에 보여줄 상대 이름
- `TargetIp`: 친구/상대에게 보낼 때 사용할 IP
- `LegacyIpRoomKey`: 기존 IP 기반 방에서 넘어온 경우의 이전 key
- `Group`: 그룹방일 때의 그룹 정보

1차 구현에서는 별도 `KnownPeer` 저장소를 새로 만들지 않고, `Friend`와 `ChatListItem`을 합쳐 UUID -> IP 매핑을 찾습니다.

### Packet / Message

패킷은 송신자 UUID를 반드시 싣습니다.

- 기존 `PacketEntity.UserUUID`는 wire 호환성을 위해 유지합니다.
- 수신 시 `packet.UserUUID`를 검증해 메시지 처리 단계에 전달합니다.
- `MessageEntity`에는 `SenderUserUuid`를 추가해 채팅 저장/표시/방 키 계산에서 사용할 수 있게 합니다.
- 송신 메시지 생성 시에도 `MessageEntity.SenderUserUuid`에 내 `UserUuid`를 함께 넣습니다.
- `SenderIp`는 사람 식별자가 아니라 수신 패킷이 알려준 주소 정보입니다.
- 수신 처리에서 같은 `UserUuid`의 친구를 찾으면 메시지/채팅방 매칭은 친구의 고정 `TargetIp`로 보정하지만, 친구의 저장 IP 자체는 변경하지 않습니다.
- IP 값 우선순위는 `packet.MyIp` -> `message.SenderIp` -> TCP remote endpoint 순서로 읽되, 이 값은 자동 저장 IP가 아니라 매칭 후보입니다.

### 개인 채팅방

개인 채팅방 key는 UUID를 알면 UUID 기준으로 만듭니다.

- UUID를 아는 상대: `user_{uuid}`
- UUID를 모르는 상대: 기존 IP room key를 임시로 사용
- 기존 DB에 저장된 IP room key는 UUID를 알게 되는 순간 `user_{uuid}`로 병합합니다.
- 같은 UUID의 방이 이미 있으면 메시지는 `MessageId` 기준으로 중복 제거하면서 합칩니다.

예:

- 기존: `192.168.0.31`
- 전환 후: `user_866a497c-245c-48cb-87b1-210882633a0f`

### 그룹

그룹 자체 식별자는 현재 `GroupEntity.Key`를 유지합니다.

- 그룹 방 key는 계속 `group_{Group.Key}`입니다.
- 그룹 구성원은 `Members`의 `Ip` + `UserUuid` 힌트를 기준으로 관리합니다.
- 기존 `Ips`는 legacy 및 전송 fallback 용도로 유지하며 자동 변경하지 않습니다.
- 전송 시에는 `Members.UserUuid` -> 친구의 고정 `TargetIp` -> 그룹의 `Ips` fallback 순서로 실제 IP를 찾습니다.
- 내 포함 여부는 `UserUuid`로 먼저 판단하고, legacy 그룹에서는 기존 IP 판단을 fallback으로 사용합니다.
- 그룹 생성, 그룹 채팅 송신, 그룹 채팅 수신, 앱 시작 시점에 `Members`의 UUID 힌트를 최신화합니다.
- 그룹 메시지 수신 시 발신자의 `Ip` + `UserUuid`가 그룹 `Members`에 없으면 보존합니다. 이때 기존 멤버 UUID가 있으면 덮어쓰지 않고, 완전히 새 멤버일 때만 legacy `Ips`에도 추가합니다.
- 그룹 `Members`에 있는 UUID는 기존 친구 목록의 빈 `UserUuid`를 보강하는 힌트로 사용합니다.
- 친구 목록 보강은 기존 친구가 같은 IP 또는 같은 UUID로 이미 있을 때만 수행합니다. 그룹에만 있는 모르는 사람을 친구 목록에 자동 생성하지 않습니다.
- 친구의 `UserUuid`가 이미 있으면 즉시 건너뜁니다.
- 친구의 저장 IP는 어떤 경우에도 그룹 힌트나 수신 패킷으로 자동 변경하지 않습니다.

## 처리 규칙

### 송신

- 1:1 메시지를 보낼 때 친구의 `UserUuid`가 있으면 방 key는 `user_{uuid}`입니다.
- 친구의 `UserUuid`가 없으면 기존 IP 기반 방 key를 사용합니다.
- 실제 TCP 전송 대상은 항상 친구의 고정 `TargetIp` 또는 사용자가 입력한 IP입니다.
- 패킷에는 내 `UserUuid`, 내 닉네임, 대상별 outbound IP를 같이 보냅니다.
- 메시지 본문에도 내 `SenderUserUuid`를 넣어 패킷 메타데이터가 없어도 로그/재전송 처리에서 식별자를 유지합니다.
- 상대 UUID를 알고 있어도 `TargetIp`가 없으면 전송할 수 없으므로 친구 관리 화면에서 IP 입력을 요구합니다.

### 수신

- 수신한 `packet.UserUUID`가 유효하면 이것을 송신자 기준 식별자로 사용합니다.
- 같은 UUID의 친구가 있으면 수신 메시지를 그 친구의 고정 `TargetIp` 기준 대화방으로 묶습니다.
- 같은 UUID의 친구가 없고 같은 IP의 legacy 친구가 있으면 그 친구에 `UserUuid`만 연결합니다.
- 어떤 경우에도 수신 패킷의 IP로 친구의 저장 IP를 자동 변경하지 않습니다.
- 둘 다 없으면 친구 목록에는 자동 추가하지 않고, 채팅 목록에만 UUID 기반 미등록 상대방으로 표시합니다.
- 메시지 방향은 `SenderUserUuid == MainData.currentUser.UserUuid`를 먼저 사용하고, UUID가 없는 legacy 메시지만 IP 비교로 판단합니다.
- 그룹 메시지를 받으면 발신자 UUID와 그룹 `Members`의 UUID 힌트를 먼저 반영합니다.
- 그룹 힌트로 친구 UUID를 보강할 수 있으면 저장하되, 모르는 그룹원은 친구 목록에 자동 생성하지 않습니다.

### 친구 추가 UX

- 1:1 미등록 채팅방 헤더에는 `+` 친구 추가 버튼을 표시합니다.
- `+`를 누르면 친구 관리 창을 열고 수신/대상 IP를 미리 입력합니다.
- 상대 앱이 켜져 있으면 친구 추가 창에서 해당 IP로 연결 확인을 시도하고 `UserUuid`, 닉네임을 받아옵니다.
- 조회에 성공하면 상대가 지정한 닉네임을 이름 입력칸에 자동 입력하고, 사용자는 저장 전 이름을 수정할 수 있습니다.
- 친구 저장 시에는 사용자가 최종 입력한 이름과 조회된 `UserUuid`를 같이 저장합니다.
- 조회에 실패하면 "상대방의 프로그램이 꺼져있거나 없는 IP 입니다"를 표시하고, 사용자는 이름/IP를 직접 입력해 저장할 수 있습니다.
- 조회 성공 여부와 관계없이 저장 IP는 사용자가 입력한 IP를 유지합니다.
- 조회 결과가 내 `UserUuid`와 같거나 IP가 본인/loopback이면 자기 자신이므로 친구 추가를 막습니다.
- 친구 추가가 완료되면 `{이름}님이 추가되었습니다.` 안내를 표시합니다.
- 사용자는 열린 창에서 이름만 입력하거나 수정한 뒤 추가합니다.
- 그룹 채팅의 그룹원 목록에서도 친구가 아닌 IP 옆에 `+`를 표시합니다.
- 그룹원 `+`도 같은 친구 관리 창을 열며, 해당 그룹원의 IP를 미리 입력합니다.
- IP는 `packet.MyIp`, `message.SenderIp`, 그룹의 `Ips` 목록을 우선 사용하고, 필요 시 TCP remote endpoint를 fallback으로 사용합니다.

### 마이그레이션

- 사용자 파일: `UserUuid`가 없으면 생성 후 `user.dohi`로 저장합니다.
- 친구 파일: 기존 `Name`은 표시 이름, 기존 `Ip`는 고정 전송 대상 IP로 보정합니다.
- 채팅 목록: UUID가 있는 개인방은 `user_{uuid}`를 `UniqueKey`로 사용합니다.
- 채팅 DB: 기존 IP room key는 바로 삭제하지 않습니다.
- UUID가 확인되는 시점에 기존 IP room key의 메시지를 `user_{uuid}` room key로 이동합니다.
- 병합 중 같은 `(room_key, message_id)`가 있으면 1건만 유지하고 실패 상태 같은 최신 상태를 반영합니다.

### 충돌 처리

- 하나의 UUID가 여러 IP에서 보여도 친구의 고정 IP를 자동 변경하지 않고, 수신 메시지만 UUID 기준으로 기존 친구/방에 묶습니다.
- 하나의 IP에서 서로 다른 UUID가 번갈아 보이면 IP를 기준으로 친구를 덮어쓰지 않습니다.
- UUID가 같은 친구가 이미 있는데 다른 legacy 친구에 같은 UUID를 연결해야 하면 자동 병합하되, 표시 이름은 사용자가 직접 지정한 값을 우선합니다.
- 내 UUID와 같은 UUID가 수신되면 내 메시지/자기 자신으로 판단하고, 친구로 자동 등록하지 않습니다.

## 구현 순서

1. UUID 정규화/검증 helper를 추가합니다.
2. `Friend`에 `UserUuid`, `DisplayName`, `TargetIp`, `LastSeenNickname`을 추가하고 기존 `Name`, `Ip`를 이행합니다.
3. `PacketReceiver`에서 `packet.UserUUID`, `packet.MyIp`를 `MessageEntity`에 반영합니다.
4. 개인 채팅방 key 계산을 `UserUuid` 우선으로 바꿉니다.
5. `ChatListItem`에 개인방 UUID와 legacy IP 정보를 분리합니다.
6. `ChatLogStore`에 room key 병합 API를 추가합니다.
7. 그룹 구성원을 UUID 기준으로 저장하되 기존 `Ips` fallback을 유지합니다.
8. 친구 관리/그룹 생성 UI에서 UUID를 몰라도 IP만으로 등록할 수 있게 두고, 수신 시 자동 보정합니다.

## 완료 조건

- 같은 사용자의 IP가 바뀌어도 기존 대화방이 유지됩니다.
- 그룹 구성원이 IP 변경으로 이탈 처리되지 않습니다.
- 메시지 방향 판정이 다중 NIC 환경에서도 안정적입니다.
- 기존 사용자 데이터가 자동으로 이전됩니다.
- UUID가 없는 구버전 패킷도 수신 가능하며, 이 경우에만 IP 기반 legacy 처리를 사용합니다.
- 친구가 없는 상대에게서 메시지를 받아도 채팅방은 열리지만 친구 목록이 임의로 오염되지 않습니다.
- 같은 UUID의 기존 IP 방과 신규 UUID 방이 병합되어 메시지가 중복 표시되지 않습니다.

## QA 체크리스트

- 신규 설치에서 `user.dohi`가 생성되고 앱 재시작 후에도 같은 `UserUuid`가 유지되는가.
- 기존 `user.json`만 있는 환경에서 `user.dohi`로 이행되고 UUID가 보정되는가.
- `127.0.0.1`로 자기 자신에게 보내는 로컬 echo 테스트가 화면에 표시되는가.
- 로컬 echo는 같은 `MessageId`를 DB에 중복 저장하지 않는가.
- 전송 실패 테스트는 `999.999.999.999`처럼 잘못된 IP가 아니라 `192.0.2.1`처럼 유효하지만 도달하지 않는 테스트 IP로 확인하는가.
- 같은 UUID가 다른 수신 IP로 들어와도 친구의 고정 IP는 바뀌지 않고 같은 개인 채팅방에 쌓이는가.
- 같은 IP를 쓰던 다른 사용자의 UUID가 들어왔을 때 기존 친구가 잘못 덮어써지지 않는가.
- UUID가 없는 구버전 클라이언트 메시지가 기존처럼 수신되는가.
- 그룹 멤버 IP가 바뀌어도 UUID 기준으로 그룹 메시지를 받을 수 있는가.
- 내 UUID가 포함된 그룹에서는 내 포함 여부가 IP가 아니라 UUID 기준으로 판단되는가.
- room key 병합 후 `ChatMessages.db`에서 메시지 중복이 생기지 않는가.
